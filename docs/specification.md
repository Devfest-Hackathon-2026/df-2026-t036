- 開発体制: 3人

- 記号: **確定**＝会話で合意済み、**暫定**＝推奨案として採用・運用テストで調整可、**未定**＝決定待ち。

## 1. ビジョン・ミッション・サービス原則

### ビジョン
誰もが創作を通じて、自分の可能性を広げられる世界。知名度・実績・金銭事情に左右されず、アイデアを持つ人と絵を描く人が出会う。

### ミッションイラスト交換
「描いてほしい」と「描いてみたい」をつなぎ、創作を新しい出会いと機会に変える。

### 解決したい課題
- **お題主**: 有償依頼の負担、知らない描き手への声かけの難しさ、自分のアイデアを描いてもらう機会の少なさ。
- **描き手**: 実績や認知度が不足し依頼を得にくい、絵柄や技術を実作品で示す機会が少ない、描くお題を探したい。

### 設計原則
- 競争、ランキング、フォロワー数よりも、自発的な創作と個別の受け渡しを重視する。
- アカウントを「お題主専用」「描き手専用」に分けない。1人が両方の行為をできる。
- アイデアは公開するが、**受信済みイラスト画像は受信者（お題主）だけが閲覧可能**。描き手は送信前プレビューはできるが、送信確定後はアプリ内で画像を閲覧できない。
- 創作者の外部SNSとの連携・外部共有支援はM2以降。M1では受信者による端末への画像保存を許可する。

## 2. マイルストーン・対象範囲

### M0：開発基盤
**目標**: 3人が独立した担当を並行実装し、安全に統合できる状態をつくる。

- Flutter Webプロジェクト、GitHub、ブランチ運用、共通コーディング規約。
- Firebase Authentication（Googleログイン）、Cloud Firestore、Cloud Storageの初期構築。
- Firebase HostingとCloud Run（FastAPI）のデプロイ環境。
- Firestore/Storage Security Rules、Cloud Runの認証検証、環境変数・権限・予算アラート。
- データモデル、API契約、ルーティング、共通UI部品、テストデータの初期定義。

**M0完了条件**: Flutter Webから認証し、API経由のFirestore読み取りとテスト用Storage操作、Cloud Run認証付きAPI疎通、Hosting公開、CI/手動デプロイ手順を確認できる。

### M1：ハッカソン版
**目標**: お題を公開し、他者がイラストを送り、お題主が受け取り・いいね・保存できる一連の体験を完成させる。

**範囲**: Webブラウザ（スマホ・iPad・PC）での利用、ハッカソン版、4項目ナビゲーション、アイデア5スロット、ピン、作品送信、受信箱自動更新、履歴、期限処理、削除。

**M2以降**: 興味順TL、検索、作品の外部SNS共有支援、SNSリンク・プロフィール充実、レコメンド、ランキング、ネイティブアプリ・プッシュ通知、透かし、AI画像判定など。M1に持ち込まない。

## 3. 画面構成・ナビゲーション

### フッター（スマホの4項目）【確定】
1. **タイムライン**: 「新着順」「ピン留め」のカテゴリ切替。興味順・検索はM2。
2. **アイデア**: 5つのスロットへの装填、掲載中アイデアの確認・削除、空きスロットから投稿。

通知ベル・通知一覧は設けない。PC・iPadは幅に応じてナビゲーションを最適化する。

## 4. 共通カードコンポーネント

### `IdeaCard`
| 表示種別 | 表示するもの | 主操作 |
|---|---|---|
| `timeline` | 投稿者、タイトル、説明の抜粋、タグ、投稿時間、ピン状態、TL掲載残り | 詳細、ピン操作 |
| `pinned` | タイトル、投稿者、説明抜粋、**受付残り日数** | 詳細、ピン解除 |
| `slot` | スロット番号、タイトル、TL掲載残り時間／空き状態 | 本人用詳細または投稿 |
| `ideaHistory` | タイトル、投稿日時、状態（掲載中／ピン受付中／受付終了）、削除 | 本人用詳細 |
| `drawnHistory` | **他人のアイデア情報をID参照で取得**、送信日時、描画済み、いいね状態 | アイデア詳細、参照できない場合はエラーカード |

### `ArtworkCard`
- 受信箱だけで使用。権限のある受信者に、正規化画像、元のお題名、作者名、受信日時、残り閲覧期間、未読印、いいね状態を表示。
- 作品カードから受信作品詳細へ遷移。送信者向けの作品画像カードは作らない。

### 共通表示ルール【暫定】
- タイトルはカード内で最大2行、説明は最大3行、省略部分は詳細画面で確認。
- タグはカード上で最大2個＋残数、詳細では全件。
- 削除はカードで即実行せず詳細画面の確認ダイアログから行う。
- 期限まで24時間未満は注意表示。期限判定はサーバー時刻基準。
- 取得不可と一時的な通信障害を分ける。非公開対象の存在はエラー応答で漏らさない。

## 5. アイデアの仕様

### 入力・作成
- タイトル: **最大40文字**【確定】。必須。
- 説明: **最大600文字**【確定】。必須。
- タグ: 任意、最大5個、各20文字以内、重複を排除【暫定】。
- M1ではお題への画像添付なし。
- 投稿前にプレビュー・確認画面を表示し、**投稿後の編集は不可**【確定】。
- 下書き専用保存はM1では用意しない【暫定】。入力途中に戻るときは破棄確認。
- 投稿時にCloud Runでスロット空き、入力、重複リクエストを検証する。

### 5スロット方式【確定】
- 5スロットは「**現在TL掲載中のアイデア最大5件**」。生涯投稿数の上限ではない。
- 空きスロットを押すと投稿画面へ進み、投稿確定で装填。
- **投稿7日後**にTL掲載終了・スロット自動解放。アイデアそのものは消えない。
- 投稿者は使用中スロットから手動削除できる。掲載終了後はマイページのアイデア履歴から削除できる。
- アイデア履歴は原則保持し、本人による手動削除は論理削除とする。30日で自動削除しない。

### 公開・ピン・受付
| 期間（投稿時刻を起点） | TL | 誰が閲覧・投稿可能か | スロット | アイデアの保持 |
|---|---|---|---|---|
| 0日以上～7日未満 | 新着に掲載 | ログイン利用者はアイデア閲覧・イラスト投稿可。自分のお題に自分では送れない | 使用中 | 保持 |
| 7日以上～30日未満 | 新着から除外 | 未送信者の投稿は**事前ピンを保持するユーザー**のみ。お題主・送信済み描き手は履歴閲覧可、再投稿不可 | 解放 | 履歴にも保持 |
| 30日以降 | 非表示 | 新規受付不可、全ピン解除。お題主と過去に描いたユーザーの履歴経由でのみ閲覧可 | 解放 | 履歴として保持 |

- ピン上限は1ユーザー最大5件【確定】。7日経過後の新規ピン登録は不可【暫定】。
- **7日経過後にピンを解除すると、そのアイデアへの投稿権限を失う**【確定】。
- 30日で受付を終了し、ピンを自動解除。アイデア本体は保持【確定】。
- 自分のお題もTLに表示し、「自分の投稿」と明示。自分のお題へのピン・作品送信は不可【確定／暫定】。

### 手動削除【確定】
- 掲載中は「アイデア」画面の使用中スロットから、掲載終了後はマイページのアイデア履歴から削除。
- 確認ダイアログで不可逆、TL・ピン非表示、新規受付停止、既存作品は維持されることを説明。
- 削除すると新規投稿受付は即停止し、ピンは無効。**すでに届いた作品は各作品の送信から7日間保持**。
- 手動削除分はマイページのアイデア数に含めない。期限満了分は含める。
- 過去の描いた履歴はID参照が失敗しても記録を残し、カード単位で「参照できません」と表示する。

## 6. イラスト投稿・受信・いいね

HEIC/HEIF対応を維持する。サムネイルは作らず、正規化画像1枚を表示・ダウンロードに共用する。通信失敗は同じ画面内で再試行できるが、タブ終了後のアップロード再開は対象外。同じuploadIdの再試行では、セッション・入力世代・変換仕様の一致を確認した完成画像を上書きせず再利用し、投稿資格を再確認してDB確定する。

### イラスト投稿【確定／暫定】
- 1ユーザーにつき**1アイデアに1作品**。自己投稿不可。送信確定後の差し替え・取消不可。
- M1では画像1枚のみ、添付コメントなし。投稿前プレビュー、確認、送信進捗・失敗時の再試行を用意。
- 対応形式【確定】: PNG、JPEG、WebP、HEIC/HEIF。PSD、`.procreate`、動画、アニメーションGIFはM1非対応。
- 目安: 元画像30MB以内、正規化後10MB以内、長辺2,560px上限【暫定】。PNG等の透過は保持し、EXIF等の位置情報を削除。
- **Flutter Webでサイズ・形式の事前チェック** → 必要な形式・容量の場合のみCloud Runで変換／最適化。Cloud Runでも実データを再検査。
- 送信確定時にCloud RunがFirebase IDトークン、受付期限、ピン状態、重複投稿を検証。画像をStorageに保存して、作品ドキュメントと描いた履歴を確定。
- 作品には**投稿時点のアイデア情報のスナップショット**（タイトル等）を複製し、お題が後で削除されても受信作品を独立して表示できるようにする。
- `sourceIdeaId`、`artistId`、`recipientId` は別途保持し、権限・重複投稿判定・期限削除に使う。

### 受信・閲覧権限【確定】
- 受信箱はお題主宛に届いたイラストを**新着順**で表示し、未読マークを付ける。
- **送信確定後、作品画像と受信作品詳細を閲覧できるのは受信者（お題主）だけ**。描き手や第三者は不可。描き手は自身の原画を手元で保持する前提。
- 受信者は投稿後7日以内にいいね・ダウンロード可能。ダウンロードは変換・圧縮済みの保存版を使用【確定】。
- 作品の端末保存はM1で許可。サービス内からのSNS共有操作はM2。端末に保存されたファイルは7日後のサーバー削除の対象外。
- 永続キャッシュ・オフライン閲覧はM1では実装しない。通常の一時的な画面描画キャッシュは許可。ただし期限切れ後はアプリ側の表示を停止する。

### いいね【確定】
- いいねは1種類。**お題主のみ**操作でき、作品ごとに0/1。
- 作品の閲覧可能な7日間に一度だけ追加でき、取消不可。描き手の「もらったいいね数」に反映。
- 描き手のマイページ「描いた履歴」アイデアカードにいいね済み状態を表示。作品自動削除後も最終状態を保持。
- 受信者による作品の手動削除を許可【暫定】。この場合、作品画像を削除し、付いていたいいねと累計は維持する。描いた履歴と描いた数は維持。
- 公開のいいねランキング・誰でも押せるリアクションは実装しない。

### 保存期限【確定】
- イラストは**作品投稿時刻から7日間**だけ受信箱・受信詳細で表示する。
- 7日経過した時点で閲覧権限を失わせ、Cloud Runの削除処理でFirestoreの作品情報とCloud Storage画像を削除する。
- 作品の7日削除は**描いた履歴や累計数を消さない**。描いた履歴は「送信した先のアイデアID＋送信日時＋いいねの最終状態」などの軽量情報として永続保持。
- 投稿29日目に送信された作品も、アイデアが30日で受付終了した後、作品自身の7日目までは受信者が閲覧できる。

## 7. マイページ・設定・受信箱更新

### マイページ【確定】
- ランダム生成されたニックネーム表示。
- **アイデア数**: 手動削除していない投稿の累計（30日満了による受付終了では減らない）。
- **描いた数**: 送信完了した作品数の累計。7日後の作品削除でも減らない。
- **もらったいいね数**: 受け取ったいいねの累計。取消不可であり、期限切れ・受信者による作品手動削除後も保持。
- **アイデア履歴**: 公開中／ピン受付中／受付終了を区別し、原則永続表示。手動削除が可能。
- **描いた履歴**: 送信先のアイデアをIDで参照し、IdeaCardを永続表示。受信イラスト画像は描き手に表示しない。参照先が削除で見つからない場合はエラー状態のカードを表示し、描いた実績は保持。

### 設定・受信箱の自動更新（確定）
- 名前は初回登録でサーバーがランダム生成し固定する。変更画面・変更APIは作らない。
- Googleアカウントの認証情報表示、ログアウト、規約・連絡先を用意する。
- 通知ベル・通知一覧・通知データは作らない。受信箱は表示中かつ前面の間だけAPIを定期取得する（3分（180秒））。背景・画面離脱で停止し、復帰時に即取得する。
- 受信箱の自動更新だけでは既読にしない。受信者が詳細画像を表示した後、専用APIで初回readAtを記録する。
- 自動更新成功時は先頭ページで一覧を置き換え、後続ページ・旧カーソルを破棄する。更新失敗時は一覧を維持し、更新前の遅延応答は混ぜない。

## 8. 削除・欠損データ

### アカウント退会（対象外）

退会画面・API・自動削除フローは今回作らない。作品の期限削除・手動作品削除・お題削除は残す。

### 欠損・通信エラーの扱い【確定】
- アイデア／描いた履歴は内部IDで管理し、Flutterが参照先を取得する。
- 存在しない・権限がない対象は共通の「参照できません」。通信障害: 「読み込みに失敗しました／再試行」。**一覧全体ではなくカード単位でエラー表示**。
- データの取得可否はFastAPIが判定し、Firestore直接アクセスはRulesで拒否する。IDを知っているだけで閲覧可能にはしない。

## 9. 技術構成・責務

```text
Flutter Web (Firebase Hosting)
 ├─ Firebase Authentication（Googleログイン）
 ├─ Firestoreへの直接アクセスなし（データ取得・更新はFastAPI）
 ├─ Cloud Storage（認可済みの一時アップロード）
 └─ Cloud Run / FastAPI（認証付きAPI）
      ├─ アイデア作成・削除／5スロットの同時実行制御
      ├─ 作品送信の検証・確定／画像検証・必要な変換
      ├─ 作品の受信者限定配信・ダウンロード認可
      ├─ いいね・累計値のトランザクション更新
      └─ 作品・一時画像の削除
Cloud Scheduler → Cloud Run（作品期限削除、30日後ピン整理、放置アップロード回収）
Firestore + Cloud Storage（恒久データ、期限付き画像）
```

- **Flutter側**: 形式・サイズの事前判定、フォーム・UI、必要なデータ取得、認証トークン送付、プレビュー。
- **Cloud Run側**: IDトークン検証、業務ルールの再検証、画像形式の実体確認・必要時変換、複数データの整合性更新、認可済み画像配信、削除。
- **Firestore/Storage Rules**: クライアント直接アクセスの制限。Cloud RunのAdmin SDKはRulesをバイパスするため、API側でも明示的な認可が必須。
- 作品画像は公開URLや長期有効のトークンURLで配布しない。受信者に認証済みの配信API等を通して提供する。
- 日時はUTCのサーバー基準。全期限チェックで `createdAt + 7日 / +30日` を使用し、定期削除が遅れても**閲覧・受付を期限時点で禁止**する。

### 採用コレクション（B案・通知なし）

| 保存パス | 主な役割 |
|---|---|
| `users/{uid}` | ニックネーム・非公開の状態・累計 |
| `userSlots/{uid}` | 掲載枠。usersとは独立 |
| `userPins/{uid}` | ピンしたお題ID。usersとは独立 |
| `ideas/{ideaId}` | お題。30日経過で自動削除しない |
| `artworks/{submissionId}` | 受信作品。送信から7日 |
| `users/{uid}/drawnHistory/{submissionId}` | 描き手の履歴。作品消滅後も保持 |
| `uploadSessions/{uploadId}` | 一時画像の所有者・期限・確定状態 |

階層・認可・トランザクションの詳細は [DB仕様書](database/DB_v0.md) を参照。履歴はusers配下、通知コレクションは設けない。専用のjobs・idempotencyKeysは設けず、削除状態と同じお題IDの再送で対応する。メンテナンスはサーバー設定で切り替え、通常APIへ503を返す。

### API契約のたたき台（M0で確定）
| メソッド・パス例 | 概要 |
|---|---|
| `POST /ideas` | スロット空きと入力を検証して作成 |
| `DELETE /ideas/{ideaId}` | 投稿者のみ手動削除 |
| `POST /artworks/prepare` | アップロードの準備・投稿資格の事前確認 |
| `POST /artworks/commit` | 画像実体・投稿資格を再検証、作品＋履歴を一意に確定 |
| `GET /artworks/{id}/image` | 受信者だけに作品画像配信 |
| `GET /artworks/{id}/download` | 受信者だけに圧縮版をダウンロード |
| `POST /artworks/{id}/read` | 受信者の初回既読を記録 |
| `POST /artworks/{id}/like` | 受信者だけがいいね追加（取消不可） |
| `DELETE /artworks/{id}` | 受信者による作品削除 |
| `POST /internal/cleanup` | Scheduler等から認証付きで期限切れ処理 |

このAPI表は**候補**。TL・プロフィール・作品既読を含む全データ操作をFastAPI経由とし、nicknameはusersへ統合する。パス・入出力の詳細はDB・API仕様書のレビュー案で確認する。重複投稿や二重加算を防ぐ冪等キーを用いる。

## 10. 権限・安全対策

| 操作 | 自分のお題のお題主 | 他人のお題の描き手 | 無関係の利用者 |
|---|---|---|---|
| TL期間中のお題閲覧 | 可 | 可 | 可 |
| 7〜30日のピン経由のお題閲覧 | 可 | 事前ピン保持または送信履歴があれば閲覧可 | 不可 |
| 30日以降のアイデア履歴閲覧 | 可 | そのお題に投稿した履歴があれば可 | 不可 |
| 作品画像の閲覧・保存 | **受信者のみ可** | 不可 | 不可 |
| いいね操作 | **受信者のみ可** | 不可 | 不可 |
| お題の手動削除 | 可 | 不可 | 不可 |

- Googleログインで参加可能。通報・ブロック専用UIはM1では作らず、問題は管理者へ直接連絡【確定】。
- 管理者による問題投稿・画像の削除、アクセス停止、エラーログ確認は可能にする。
- ファイル検証、Storageアクセス権、認証済み画像取得、作品の既読・期限削除をテストする。
- 不正な投稿・削除による累計数操作や同時実行バグを防ぐ。

## 11. 3人の担当分担（仮割り当て）

| 担当 | 主責任 | M0 | M1 |

| **B：Firebase・アイデア** | データ・認証・アイデアロジック | Firebase Auth、Firestore、Rules、データモデル | 5スロット、TL、ピン、お題作成/削除、履歴の参照権限 |
| **C：Cloud Run・作品** | API、画像、期限と運用 | FastAPI/Cloud Run、Storage連携、Scheduler準備 | アップロード/変換、作品確定、受信限定配信、いいね・作品既読、自動更新、画像削除 |

- Aが共通UIを先に固め、B・Cは事前に合意した型・API契約に沿って並行実装。
- Cの負荷が高くなりやすいため、Bはお題期限・ピン削除処理、Aはマイページ・設定のUIを積極的に分担。
- 全員でSecurity Rules/API認可のレビューと、実機iPadを使った統合テストを行う。
- チーム各人の経験と実際の担当名は**未定**。

### 実装順序
1. M0: データモデル・権限・API契約・共通UIを合意。
2. M1前半: 認証 → アイデア投稿 → TL → 5スロット → ピン。
3. M1中盤: イラスト選択・変換 → 送信確定 → 受信箱 → いいね・履歴。
4. M1後半: 受信箱自動更新・既読 → 期限削除・放置画像回収 → 全体テスト。
